| Question | Answer |
| --- | --- |
| What changes first, and why? | The first implementation commit adds `.c2/config.yaml` requesting exactly base `ubuntu*` and capability `kvm`. I will then add the verify hook early, before substantive runtime code. This requests the testing environment needed for real native qualification. |
| Where will provider data live by default? | Shared settings use `~/.pulse/cloudhypervisor/config.json`; owner state, prepared sources and disposable disks use `~/.pulse/cloudhypervisor/owners/<owner>/`. The library and setup/upgrade/server share this resolution. Explicit paths take precedence, with private owner locks and credential protections unchanged. |
| Which home is used, and what if it is unavailable? | I will resolve the process user's home once when a default is needed, then use absolute paths. Missing or unsafe home/storage paths fail without falling back elsewhere. Explicit absolute paths work without a home default. Runners retain the resolved path across provider/SDK closure; changing homes does not migrate or rediscover old state. |
| Does dispatch acceptance mean a successful job? | No. I will return accepted only after native dispatch acknowledgement, with an empty reason. Boot, lease validation and job completion remain separate observations. Ambiguous native responses stay unknown and reserve capacity. |
| How does execution survive SDK or controller loss? | Each runner gets a systemd unit outside the provider service's cgroup. A detached subprocess alone cannot survive service-manager cgroup cleanup reliably. Hosts without independent supervisor authority fail preflight. |
| What survives crashes without retaining credentials? | I will persist ownership, intent, reservations, dispatch phase and duplicate fences, never serialized launches or leases. One native start attempt and durable guest intent prevent duplicate VM/worker starts. Missing delivery cannot be repaired by replaying a lease. |
| When may capacity and resources be released? | Only exact ownership plus native termination evidence permits cleanup. Unreachable sockets, stale PIDs, old age or absent list entries are insufficient. Corrupt or mismatched state remains quarantined and accounted for. This can require operator intervention rather than risk deleting unrelated work. |
| How are caps enforced after failures? | Positive caps start at native dispatch, include boot time and use a monotonic runner deadline with a systemd backstop. Zero adds no execution cap. Boot grace may terminate only a VM proven never to have started c2j; uncertainty preserves the worker. |
| How are resources and capabilities justified? | I will resolve concrete native bases, verify preparation identity and use guaranteed usable profiles below nominal guest capacity. Arbitrary requested or configured claims cannot become allocation facts. Busy/warming qualified bases remain discoverable, while admission still checks readiness and budgets. |
| What prevents overload or a warming queue? | Serialized durable reservations account for jobs and preparation builders across slot, CPU, memory and disk limits. Busy, warming or zero-count pools decline immediately without keeping a lease for later execution. Reduced capacity drains rather than cancels accepted work. |
| How are sources upgraded safely? | Setup/reconciliation prepares verified immutable sources. Changed fingerprints select new sources; upgrade drains accepted work first. Failed preparation or maintenance timeout preserves prior sources and running jobs. An executed disk is never a preparation source. |
| How are slow log callbacks contained? | Independent contexts/durations, serial callbacks, bounded queues, active-subscription limits and callback deadlines end observation promptly. A blocked callback retains bounded capacity instead of spawning unlimited replacements. Runners continue draining after detachment. Records are at most 4096 bytes with consecutive per-launch sequences. |
