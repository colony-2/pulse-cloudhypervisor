# Cloud Hypervisor provider improvement plan

The operator should be able to prepare a Linux worker pool, start the server with the saved settings, and use a launch ID to answer three questions. How long did it take to start c2j? What did the worker do? Why and when was its VM removed? The following changes are proposed, in delivery order.

## 1. Record one virtual log per launch

Today a listener can attach at submission, but the first record arrives after image verification, disk cloning, and hypervisor dispatch. The stream carries c2j stdout and stderr, reports worker exit, and closes after the hypervisor exits. Cleanup runs separately. The provider offers no historical read. [Current runner](../internal/runner/runner.go) · [Live events](../native.go) · [Cleanup](../runtime.go)

Create a private archive scoped to the owner and launch ID, outside the disposable VM directory. Start it when the provider receives a valid launch ID, before admission or disk work. Record a decline or pre-boot failure even when there is no guest output. Duplicate submissions must leave the original timeline intact.

| When | What to record |
| --- | --- |
| Before boot | Submission received, admission decision, verification started/completed, clone started/completed, logical image bytes, clone method (reflink or copy), hypervisor process started. |
| In the guest | First guest-agent connection, c2j process started, original stdout/stderr bytes, c2j exit code or signal when known. Identify guest boot or console diagnostics separately from worker output. |
| At shutdown | Reason for shutdown, including normal exit, runtime limit, or watchdog decision. Record hypervisor exit, cleanup failures or retries, then the time resources were actually released. |

**Proposed storage.** Keep one append-only host event file covering setup *and* teardown, plus rotating segments for guest output. The runner can capture output while the controller is disconnected. Give records a durable per-launch sequence in append order across sources. Keep UTC timestamps and measure host stage durations with a monotonic clock. Readers can then return one ordered view while the VM runs and after it is deleted. A separate before-file and after-file would add little and would make watchdog events during the run harder to place.

Serialize sequence assignment and record commit across the controller and runner. On recovery, expose only committed records and mark any known loss. Drain the runner’s final output before finalizing the cleanup entry. For a launch that never produced a VM, finalize on its terminal admission or startup outcome.

Expose the archive through the SDK’s `ProviderWithLaunchLogs.GetLaunchLog` in process and reverse modes, and through `logs LAUNCH_ID [--follow]`. Keep the existing live callback. Capture must work with zero listeners and a slow reader must never block c2j. Use restart-stable page tokens, report gaps with `Incomplete`, and set `Finalized` when the archive is closed. Bound storage by age and bytes per owner. Keep lease bytes, credentials, and raw health bodies out of provider-generated events. [SDK retrieval contract](https://github.com/colony-2/pulse-provider-api/blob/bd1a5c559150/launch_log_read.go) · [macvz archive behavior](https://github.com/colony-2/pulse-macvz/blob/2044dd3/README.md#per-launch-logs)

**Acceptance.** Retrieve a launch submitted without a listener. Page and follow it across worker exit, controller restart, and VM deletion. Check byte order, distinct source labels, stable resume positions, and explicit gaps after rotation or disk failure. A failure before boot must identify the failing stage. A successful run must show submission-to-c2j and exit-to-cleanup durations.

## 2. Monitor c2j over HTTP and reap failed workers

Have the standalone server run reconciliation and a separate health monitor for accepted launches. During base preparation, verify that the pinned `c2j run with-lease` supports `--health-port` and record support with the image identity. From the host, probe the launch’s assigned guest IP at `GET /health` on port 8080. Validate the expected tenant and job, bound the response, and bypass proxies and redirects. [c2j worker health contract](https://github.com/colony-2/c2j/blob/a6de3eca42509bb9caac1ac2f8af74b37319c192/README.md#worker-health-probes)

Adopt the macvz defaults. Probe every 5 seconds with a 3-second timeout. Allow 60 seconds for startup, then require at least three failed probes spanning 30 continuous seconds. A valid response clears the failure window. Persist the last observation, current task and task start, and last known lease expiry for diagnosis. A long task or an old lease timestamp alone must never trigger a stop. Legacy images without the endpoint report `unsupported`. Unknown admission outcomes and gaps in controller observation are ineligible for failure counting. [macvz watchdog and timing](https://github.com/colony-2/pulse-macvz/blob/2044dd3/docs/worker-health.md)

Before stopping a VM, recheck its immutable launch, VM and systemd unit identities and persist the reason and cleanup intent. Confirm native termination before releasing capacity. Resume a committed cleanup after restart and start a fresh observation window for other workers. Expose a fresh read-only probe with `launches health ID --json` and the last recorded decision with `launches show ID --json`.

**Acceptance.** Exercise a healthy long job, transient outage and recovery, an endpoint that never starts, a frozen worker, a wrong-identity response, and a reused guest IP. Restart during both a failure window and committed cleanup. A sustained failure should remove exactly the affected VM and release its slot once. Another running job must finish normally.

## 3. Align the CLI, maintenance, and reverse connection

Use the published API and plugin SDK as a matched pair. Cloud Hypervisor pins `2919f1ed5e42`; the reviewed macvz implementation pins `bd1a5c559150` and exposes retained logs and reverse mutual-key authentication. Verify Pulse collector compatibility as part of the change. [Current pins](../go.mod) · [Reference pins](https://github.com/colony-2/pulse-macvz/blob/2044dd3/go.mod) · [Reference CLI](https://github.com/colony-2/pulse-macvz/blob/2044dd3/docs/server-cli.md)

| Operator workflow | Planned interface and behavior |
| --- | --- |
| Configure once | Share `--config/-f`, `--owner/-o`, `--state-dir/-s`, `--runner`, and meaningful `--help` across commands. Explicit flags override saved settings. Read existing Cloud Hypervisor JSON and preserve pinned assets, TAPs, host budgets, and owner paths. Successful setup/upgrade atomically save effective settings, including transport choices and credential references. |
| Prepare and serve | `setup` prepares missing stopped bases and reuses verified ones. Add `--c2j-version`, `--timeout`, `--bootstrap-timeout`, and `--progress auto\|linear\|interactive`. Resolve versions to immutable build inputs. Plain `server` uses the saved pool and transport settings, recovers owned launches, prepares missing sources, and reconciles continuously at `--poll-interval`. Read-only status and capability queries stay side-effect free. |
| Upgrade | Drain accepted work, build and verify the requested replacement, then switch the published source. An explicit refresh must run even if the old source passes its readiness check. Preserve the last usable source across interruption or failure and expose progress on retry. |
| Connect to Pulse | Add `--mode/-m inbound\|outbound`, `--collector/-a`, `--name/-n`, `--tls-ca`, `--tls-cert`, `--tls-key`, and `--tls-server-name`. Support mTLS over TLS, plus `--reverse-auth mutual-key` with `--reverse-transport tls\|http` and exactly one of `--shared-key-file` or `--shared-key-env`. Plaintext HTTP/2 is an explicit selection. Keep the current `--outbound`, `--ca`, `--cert`, `--key`, and `--server-name` spellings as aliases. Preserve bare-server process hosting for existing SDK callers and support a saved outbound default for managed pools. |
| Recover a reverse connection | Match macvz reconnect delays and jitter, reload credentials on each attempt, and expose `--reconnect-initial-delay`, `--reconnect-max-delay`, `--reconnect-reset-after`, `--startup-timeout`, `--shutdown-timeout`, `--rpc-concurrency`, and `--max-message-bytes`. Keep one owner/controller and never replay a submission on reconnect. |
| Set capacity | Add `--linux-capacity/-l` and `--total-capacity/-c`. Map legacy `count` to Linux capacity. An omitted total follows Linux capacity. Explicit zero drains new admission while accepted jobs finish. Apply the lower limit plus available CPU, RAM, disk, and TAPs. Continue accounting for builders and unresolved launches. Document the existing one-slot default and the Linux-only scope. |
| Inspect a running pool | Add `status`, `images`, `launches`, `launches show ID`, `launches health ID`, and `logs ID`. Support JSON for inspection, launch filters, and log offset/follow. Expose `--log-directory`, `--log-segment-mib`, `--log-backups`, `--log-compress`, `--log-max-bytes`, and `--log-max-age`. Reads must coexist with the active owner lock. |

Publish a flag-by-flag compatibility table with the release. Document how macvz’s `--vm-home` maps to Cloud Hypervisor’s owner-scoped `--state-dir`, identify the backend value for `--backend/-b`, and mark macOS base selectors and Docker companion settings as macvz-specific. Share the setup/upgrade command definitions with embedding callers so Pulse and the standalone binary use the same parser and defaults.

**Acceptance.** Drive the built binary from an existing config and from a fresh setup through server, drain, upgrade and restart. Test flag precedence, explicit zero, failure rollback, and help output. Exercise all three supported reverse auth/transport combinations with an SDK collector, reject mismatched credentials or modes, and verify that reconnecting never starts a second worker for an accepted launch.

## 4. Measure cold starts and qualify guest capabilities

Keep prepared, stopped bases with a fresh writable disk and MAC per assignment. On the managed test worker, the ext4 filesystem holding `state_dir` rejected reflinks. The test image is 2,434 MiB. The observed 8.8 seconds ran from hypervisor start to a successful guest-agent probe and excluded disk cloning. [Filesystem probe](http://db.lab.c2.run:8081/project/c2/jobs/3MZCPXQlY1Cuj57zb5XyJdyr3Fz/story) · [Boot probe](http://db.lab.c2.run:8081/project/c2/jobs/3MWO0oygaAhgglKtJqkd6OsKiiI/story)

1. Probe reflink support on the actual `state_dir` volume during setup and surface it in `status`. Compare the ext4 copy path with a reflink-capable host volume using the same image. Use the virtual log to report p50 and p95 for verification, clone, boot-to-agent, and submission-to-c2j under single and concurrent launches. Measure again on the L0 production host before deciding whether to fund idle VMs.
2. Guest KVM detection and handoff are implemented. Setup tests a nested clone only where the current host exposes EL2. A successful ordinary-user KVM and networking probe qualifies that host/base combination. Other environments keep their ordinary and Docker capacity. Existing assignments retain their original settings. [What macvz added and how it maps to Cloud Hypervisor](manual-arm64-kvm.md#what-pulse-macvz-needed)
3. The operator qualifies the candidate through its SDK catalog and actual assignments, checking both supported and unsupported hosts. Require three nested virtio disk boots, user-service supervision, peer/outer connectivity, DNS and egress, then repeat with a combined Docker/KVM assignment. Record the candidate, image, host and matched launch identity in the qualification record. The existing macOS lab continues to qualify Docker and the ordinary provider lifecycle. [Manual scripts and commands](manual-arm64-kvm.md) · [Nested lab limits](pulse-macvz-el2-qualification.md)

Run the existing ARM64/KVM acceptance suite for each affected delivery. Add focused tests for the new behavior and update the earlier live-only logging and explicit-maintenance expectations when their replacements ship. [Current verification procedure](native-verification.md)
