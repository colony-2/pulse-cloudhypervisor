# Configure isolated Cloud Hypervisor workers

I require operator-provided Linux KVM access, an independent systemd manager, fixed Cloud Hypervisor/boot/image/tool inputs, and a preconfigured IPv4 TAP/address pool. Setup does not install host packages, create bridges, alter firewall rules, provision host services or migrate Pulse/Tart. Sources and jobs use private writable copies without host filesystem mounts.

`Config` is the typed reference. Set `version: 1`, a validated `owner`, absolute binary references (`runner`, `systemd_run`, `systemctl`) and the hypervisor path/SHA-256. `user_manager` selects a qualified lingering user manager; otherwise use the system manager. Its authority must allow starting transient services, inspecting exact units and setting their runtime properties. Each runner is a separate service with `KillMode=control-group`, no restart and discarded service stdout/stderr. Positive caps arm both a monotonic runner deadline and a systemd backstop just before native dispatch. Uncapped execution has no worker runtime limit.

The default profile is four vCPUs and 8 GiB nominal memory, with one slot. Explicit `count: 0` drains admission. Set conservative `host_cpu_millis`, `host_memory_bytes` and `host_disk_bytes`; zero budgets permit no launches. The provider counts durable assignment and builder reservations and checks native host resources before dispatch. Each configured network entry contains a distinct pre-existing `tap` and guest `address`, plus `gateway`, contiguous IPv4 `netmask` and `dns`. The guest configures its own `eth0` from fixed boot parameters. The operator remains responsible for host routes, DNS reachability and JobDB/Git/cache egress.

Each `bases` entry must be `ubuntu-24.04-arm64` on its native architecture. Disk, kernel, optional initramfs and preparation script reference absolute paths and SHA-256 digests. `recipe` is the script digest. `tools` pins the actual installed executable bytes for `c2j`, `nix`, `docker` and `guest-agent`. `docker_fixture_digest` selects a fixed guest-local Docker image by `sha256:` identity; verification never pulls a mutable tag. Only verified Docker capability is currently supported. Set usable CPU and memory below measured guest capacity; preparation reserves guest OS memory and rejects stronger claims.

The stopped Ubuntu bootstrap disk must already contain the guest command and [guest service](../guest/pulse-cloudhypervisor-guest.service), UID/GID 1000 with `/home/worker`, systemd-resolved, `/usr/sbin/ip`, and a working boot layout with root on `/dev/vda1`. The pinned preparation script runs inside a disposable builder. It installs fixed Nix/c2j/tools and configures guest-local Docker access for UID/GID 1000. Verification runs tool and Docker checks as that unprivileged user. It measures executable hashes, Ubuntu identity, architecture and usable resources, then clears guest machine identity. A source containing worker intent is rejected. Publication happens only after the exact builder's native termination is confirmed; failure preserves earlier sources.

Every accepted assignment gets a stopped-source clone, fresh machine identity/MAC and private API/vsock endpoints. The supplied lease goes through authenticated same-user Unix handoff, the private per-VM vsock channel and c2j stdin. It is never recovered from disk, placed in argv/environment/cloud-init or retained in provider records. c2j validates and renews the lease; the provider never claims replacement work.

Keep a stable service home or explicit state path. Owner directories are private and exclusively locked. Reopening observes existing identities and reserves uncertain work without replay. A stale PID, missing endpoint, old age or changing listing does not authorize deletion. Corrupt or foreign resources block cleanup. Reconciliation requires exact native termination evidence before deleting known owned resources. Small duplicate fences are retained indefinitely; deleting owner state ends duplicate protection and is not routine cleanup. No lease archive or historical log replay exists.

For development, use an installed approved Go toolchain on PATH with `GOWORK=off GOTOOLCHAIN=local`. Run `go test ./...`, `go test -race ./...`, `go vet ./...`, `python3 scripts/verify_test.py`, and `bash scripts/external-consumer.sh`. Cross-build both commands with `CGO_ENABLED=0 GOOS=linux GOARCH=arm64`. The external script serves the exact working candidate through a scratch file proxy, resolves API/SDK pins publicly with a clean module cache, checks for replacements, and exercises process and certificate-authenticated outbound hosts.

The full verification command remains failed until every retained assertion executes, including native KVM/systemd/JobDB suites on native ARM64 for the same candidate and fixed pins. The explicit `scripts/acceptance.sh --arch arm64` rejects wrong architectures and missing prerequisites. The private fixture descriptor/socket boundary and host preflight now exist. The developer prepares the isolated native-test fixture inside the supplied allocation under current human direction. Demonstrated allocation permission denials require a scoped repair; reboot recovery separately requires an exact disposable Linux host and external observer.
